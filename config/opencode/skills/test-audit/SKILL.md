# Test Audit

Optimize for regression confidence per maintenance cost. A test earns its place
by catching a credible failure of behavior or an independent contract.

Use the authoring gate for new or changed tests and the audit workflow for
existing coverage. For an exhaustive subsystem audit, also read
[EXHAUSTIVE_AUDIT.md](EXHAUSTIVE_AUDIT.md). Apply the same value bar in each mode.

## Authoring gate

Before writing a test, answer:

1. **Contract:** What observable behavior or invariant does it protect?
2. **Regression:** What plausible production mistake would make it fail?
3. **Unique proof:** Why wouldn't existing coverage catch that mistake? Name
   the suite that owns the contract. Extend an existing case or table when it
   can cover the risk; another layer needs a distinct failure mode.
4. **Boundary:** Can the test reach the real owner through a supported entry
   point? Avoid adding exports, flags, wrappers, or injection hooks solely to
   expose internals. Use existing architectural boundaries for dependencies.

If an answer is missing, investigate before adding the test. Choose the
smallest stable boundary that exercises the risk; an end-to-end test is not
automatically stronger than a focused unit test.

Check the smells and retention rules below. Use independently derived
expectations. A mock may supply a dependency response, but must not implement
the behavior being asserted. Negative cases must reach the intended guard.

For a bug fix, run the regression against the pre-fix behavior and observe the
intended failure, then against the repair and observe success. Use an isolated
copy or a reversible change that preserves existing user edits. If the control
cannot run, report the unverified claim and blocker rather than claiming proof.

Done when each added or changed test has a distinct contract and credible
failure, and its focused validation is recorded.

## Smells to investigate

These identify candidates, not automatic deletions:

- **No independent oracle:** self-comparisons, expected values generated by the
  subject, mocks that return the asserted result without exercising its owner.
- **Source mirrors:** copied manifests or export inventories, exact source or
  import greps, private helper or call-shape assertions that break on harmless
  refactors.
- **Duplicate proof:** the same contract replayed through multiple wrappers or
  providers without exercising a distinct integration or lifecycle risk.
- **Test-driven dead weight:** production paths, globals, reset hooks, or
  wrappers whose only callers are tests and whose contract has a better owner.
- **Vacuous coverage:** a test that only executes code without checking a
  meaningful outcome; a negative case rejected by the wrong guard; fixtures
  that supply the ordering or state transition the production owner must create.
- **False promises:** names stronger than their assertions, capability flags
  checked without their promised behavior, persistence checked against a store
  the exercised path never writes.

## Retention rules

Keep independent proof of public APIs, wire formats, storage and migrations,
security boundaries, configuration and defaults, packaging, platform behavior,
and architecture constraints. Exact bytes, exports, and call ordering can be
the contract. Source inspection can be the cheapest valid guard when it detects
a contract violation and survives irrelevant identifier changes.

Judge what the assertions detect, not the test's name or shape. A no-throw,
compile-time, or process-exit test can have an implicit oracle. Slowness, mocks,
snapshots, test size, or overlap alone do not justify deletion. Overlap is useful
when the tests catch different failures.

A valuable test that already fails may reveal a product bug. Reproduce and
report it; do not delete, skip, or weaken it to make the audit green. Keep
uncertain candidates until their unique coverage is understood.

## Audit workflow

### 1. Establish scope and evidence

Read repository and scoped instructions, test scripts, and CI selection rules.
Use the requested scope; for an unspecified audit, start with changed tests or
one coherent production owner. A review request produces findings; a cleanup
request proceeds to evidence-backed edits.

Read each candidate test in full, including fixtures and parameter rows. Trace
the production owner, entry points, callers, collaborators, and overlapping
tests. Inspect relevant history; for dependency-backed claims, inspect the
dependency's source or types. Record unavailable evidence explicitly.

Run the relevant baseline before cleanup. Then present a compact candidate
ledger to the user before the first edit. For each proposed change include:

- exact location and test name;
- the failure it actually detects;
- disposition: **retain**, **repair**, **consolidate**, or **delete**;
- remaining proof by test name and location, or why no meaningful contract exists;
- callers and history relevant to any removable production seam;
- risk and focused validation command.

Done when the user has the evidence for every proposed edit; do not defer this
ledger to the handoff. Missing history alone need not block a decision, but
missing evidence of coverage or callers does.

### 2. Make one coherent cut

Move unique assertions into their keeper before deleting overlapping coverage.
Repair weak assertions when the contract matters. Remove obsolete test support
and test-only production seams only after checking runtime consumers, public
exports, and dynamic registration; no local callers does not prove a public API
is dead. Update test discovery and CI routing when moving suites.

Keep unrelated product repairs as follow-ups unless they are in the requested
scope. Do not introduce replacement scaffolding merely to reduce test count.

Done when each removed contract has a named keeper or evidence that it was
never meaningful, and every production deletion has a caller check.

### 3. Verify preservation

Use the repository's actual commands. Run affected owner tests and relevant
sibling or integration tests; run the executable or dry-run behind a removed
static guard when applicable. Capture runner exit status and totals before
filtering output; quote those results rather than inferring counts from an
excerpt. For repaired or relocated regression coverage,
demonstrate the intended failure with a pre-fix control or targeted mutation.
Restore mutations before the final run, and avoid edits while tests execute.

Run required formatting, type checks, and repository gates, then
`git diff --check`. Review deleted assertions against the keepers; a green
suite by itself cannot prove coverage survived. Distinguish baseline failures
from new failures and checks that could not run.

Done when focused checks and required gates pass, or remaining failures and
validation limits are explicitly accounted for.

## Handoff

Report the meaningful decisions with locations, unique coverage preserved,
production simplifications, checks actually run, and unresolved risks or
follow-ups. For review-only work, present findings and proposed actions. For a
broad cleanup, include production versus test/support diff size; deletion count
is context, not a success metric.
